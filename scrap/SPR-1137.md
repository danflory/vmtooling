# Migration lint gate and runtime sidecar use different squawk binaries

## Problem Statement

Squawk is part of the DB migration pipeline at **two stages**, and the two stages do not run
the same squawk:

| stage | binary | version | provenance |
|:------|:-------|:--------|:-----------|
| commit-time lint (A6 gate) | `.venv/bin/squawk` | **2.65.0** (25,465,376 B) | **hand-placed**: `pip show squawk` → not found, absent from `requirements*.txt`, and `setup_venv.sh` installs `sqlfluff` but **not** `squawk` |
| runtime lint (migration sidecar) | `/usr/local/bin/squawk`, built from `firecontrol/docker/squawk-linux-x86_64` | **2.59.0** (21,797,416 B) | vendored, SHA-256 pinned by RFC-OW-271 (`547623c6…24cafb`), verified at image build, hash matches the running container |

The gate resolves its binary as `Path(sys.executable).parent / "squawk"`
(`firecontrol/gates/gate_sql_lint.py`) — **from the interpreter's venv**, not from the
repository.

**This document defects three breaks.**

| Break | Statement |
|:------|:----------|
| **B-1** | **Rule divergence.** The gate and the runtime lint are not guaranteed to enforce the same rule set, and a mismatch would be silent. A migration could pass the commit gate and fail at startup lint, or the reverse. |
| **B-2** | **Not reproducible.** Nothing in the repository installs the gate's binary, so a fresh clone or rebuilt venv has no squawk. The gate then raises `FileNotFoundError` from `subprocess.run([_SQUAWK, …])`, exits non-zero, and the dispatcher counts it as BLOCKED — fail-closed, but with a Python traceback, and it blocks **every** commit touching a migration until someone hand-installs the binary. |
| **B-3** | **One artifact is ungoverned.** The vendored binary the runtime trusts is not itself a registered CI, while its companion rule config `firecontrol/.squawk.toml` (UDRS 42031) is. |

## Measured impact (2026-09-18) — does it produce errors today?

Measured rather than assumed, because the answer is narrower than the risk:

| question | measurement |
|:---------|:------------|
| Do the two versions disagree on the current corpus? | **No.** Both binaries run over all 251 files of `firecontrol/sql/[VR]*.sql` (excluding `V1__Baseline.sql`) flag the **identical 42 files** — zero divergence. |
| Do the two stages even read the same rule configuration? | **Effectively yes, by accident.** `firecontrol/.squawk.toml` declares `excluded_rules = []`, which is squawk's default, so it is inert. And neither stage has it in its search path anyway: the A6 hook runs from the repo root (no `.squawk.toml` there or above), and the sidecar's CWD is `/` while the config is at `/app/.squawk.toml`. Both therefore run default rules. |
| Does this block work today, in the real clones? | **Yes — 3 of the 6 guest clones.** `Overwatch_1` has no `.venv` at all; `Overwatch_3` and `Overwatch_5` have venvs without `squawk`. In those three the A6 gate raises `FileNotFoundError` and blocks every commit touching a migration, so migrations cannot land there at all. |
| Is there any present-tense error? | **Yes, one (B-2).** On a fresh clone or rebuilt venv nothing installs squawk, so `gate_sql_lint.py` raises `FileNotFoundError`, exits non-zero, and A6 blocks **every** commit touching a migration. Fail-closed, so governance holds — but no migration can land until the binary is installed by hand. |

**Severity 1 (Critical)** — this blocks a workstream today: in three of six clones no migration can be committed, and the engine that decides the verdict is not reproducible from the repository.

**Conclusion**: B-1 is *latent* today (the versions happen to agree on this corpus, and both
use default rules); **B-2 is active now** — on a fresh clone every migration commit fails
closed, so every migration fails to land until squawk is hand-installed; B-3 is an open
governance gap. That is why the fix is worth making now rather than at leisure.

**Audit-trail note**: one intermediate `post_fix` execution (row 1384) recorded FAIL. It was
not a fix failure — two checks in the TP runner itself were wrong (step 2 flagged the gate's
legitimate venv path for *sqlfluff*; step 6 parsed the wrong output stream). The runner was
corrected and re-run (row 1385, PASS). The stray row is retained because
`delete_test_data` does not allowlist `verification.test_executions`; it is superseded by
1385 and explained here rather than hidden.

**Design refinement applied during the fix**: the two gate engines need *different* provenance
rules. squawk is a vendored binary (not pip-installable) so the **repository** artifact is the
source of truth, hash-pinned and shared with the image build. sqlfluff is pip-installable so
the **venv** is the source of truth, but it is now resolved explicitly rather than via a bare
`sqlfluff` PATH lookup, which silently depended on shell activation — the same class of
accident as the defect being fixed.

## Root Cause

Two RFCs each solved "we need a squawk" without a shared artifact contract. RFC-OW-256
(UDRS 39275) ported the OPF-014 Flyway lint gate and took the binary from the environment it
runs in — the Python venv — which is the natural choice for a commit hook and invisible to
version control. RFC-OW-271 (UDRS 40175) needed the linter inside a container image and did
the right thing there: vendor the binary in the repository with a pinned SHA-256. Neither
artifact asserted that the two must be the same binary, and no verification covered the
proposition "the gate and the runtime lint with one version".

The generalisable defect: **a tool binary consumed by a governed gate was treated as an
environment convenience rather than a governed artifact.** Everything the gate depends on for
its verdict — the rule set — was left outside the repository and unpinned, so the verdict is
not reproducible from the repository.

## Fix Description

| Fix | Change | Closes |
|:----|:-------|:-------|
| **F-1** | Make `firecontrol/docker/squawk-linux-x86_64` (the hash-pinned, RFC-OW-271 vendored artifact) the single source of truth for squawk. | B-1, B-3 |
| **F-2** | `gate_sql_lint.py` resolves squawk from that repository path (not `sys.executable`-adjacent); the hand-placed `.venv/bin/squawk` 2.65.0 is removed. | B-1, B-2 |
| **F-3** | `setup_venv.sh` provisions squawk from the repository alongside `sqlfluff`, so a fresh clone can run the gate; `sqlfluff` is pinned in `requirements*.txt`. | B-2 |
| **F-4** | Assert mechanically that the gate's squawk version equals the version baked into the migration-sidecar image, so drift fails instead of passing silently. | B-1 |
| **F-5** | Register the vendored `firecontrol/docker/squawk-linux-x86_64` as a CI. | B-3 |

## Scope

- **In scope**: the commit-time SQL lint gate, the vendored squawk artifact, the migration
  sidecar image's lint stage, `setup_venv.sh`, `requirements*.txt`, and the verification that
  keeps them aligned.
- **Out of scope**: the migration pipeline's other stages (Flyway history repair, dynamic
  migration intents, dry-run), the DB image's plpgsql_check/pgTAP provisioning, the
  `.squawk.toml` rule configuration, and the 42 pre-existing corpus findings.
