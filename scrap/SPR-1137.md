# Migration lint gate and runtime sidecar use different squawk binaries

## Problem Statement

Squawk is part of the DB migration pipeline at **two stages**, and the two stages do not
run the same squawk:

| stage | binary | version | provenance |
|:------|:-------|:--------|:-----------|
| commit-time lint (A6 gate) | `.venv/bin/squawk` | **2.65.0** (25,465,376 B) | **hand-placed**: `pip show squawk` → not found, absent from `requirements*.txt`, and `setup_venv.sh` installs `sqlfluff` but **not** `squawk` |
| runtime lint (migration sidecar) | `/usr/local/bin/squawk`, built from `firecontrol/docker/squawk-linux-x86_64` | **2.59.0** (21,797,416 B) | vendored, SHA-256 pinned by RFC-OW-271 (`547623c6…24cafb`), verified at image build, hash matches the running container |

The gate resolves its binary as `Path(sys.executable).parent / "squawk"`
(`firecontrol/gates/gate_sql_lint.py`), i.e. **from the interpreter's venv**, not from the
repository. So a migration can **pass the commit gate and fail at startup lint, or the
reverse** — the two stages are not enforcing the same rule set, and the mismatch is silent.

Three consequences, all live today:

1. **Rule divergence.** Squawk 2.65.0 (gate) and 2.59.0 (runtime) can disagree about the same
   migration file. Whichever stage a developer happens to run is not the rule set that will
   apply in the cluster.
2. **Not reproducible.** Nothing in the repository installs the gate's binary, so a fresh clone
   or rebuilt venv has no squawk. The gate then raises `FileNotFoundError` from
   `subprocess.run([_SQUAWK, …])`, exits non-zero, and the dispatcher counts it as BLOCKED —
   fail-closed, which is the right direction, but it surfaces as a Python traceback and blocks
   **every** migration commit until someone hand-installs squawk from memory.
3. **One artifact is ungoverned.** The vendored binary that the runtime trusts is not itself a
   registered CI, while its companion config `firecontrol/.squawk.toml` (UDRS 42031) is.

## Root Cause

Two RFCs each solved "we need a squawk" without a shared artifact contract. RFC-OW-256
(UDRS 39275) ported the OPF-014 Flyway lint gate and took the binary from the environment it
runs in — the Python venv — which is the natural choice for a commit hook and invisible to
version control. RFC-OW-271 (UDRS 40175) needed the linter inside a container image and did
the right thing there: vendor the binary in the repository with a pinned SHA-256. Neither
artifact asserted that the two must be the same binary, and no verification covered the
proposition "the gate and the runtime lint with one version".

The generalisable defect: **a tool binary consumed by a governed gate was treated as an
environment convenience rather than a governed artifact.** Everything the gate depends on for
its verdict — the rule set — was left outside the repository and unpinned, so the verdict is
not reproducible from the repository.

## The Fix

1. **One source.** Make `firecontrol/docker/squawk-linux-x86_64` (the hash-pinned, RFC-OW-271
   vendored artifact) the single source of truth for squawk.
2. **Point the gate at it.** `gate_sql_lint.py` resolves squawk from that repository path (or
   from a path the repository installs), and the hand-placed `.venv/bin/squawk` 2.65.0 is
   removed.
3. **Make the venv reproducible.** `setup_venv.sh` installs/copies squawk from the repository
   alongside `sqlfluff`, so a fresh clone can run the gate.
4. **Pin and assert.** Record the pinned SHA-256 once; assert at gate time that the binary's
   version matches the version baked into the migration-sidecar image, so drift is caught
   instead of discovered.
5. **Then version-bump deliberately.** If 2.65.0 is wanted, replace the vendored binary, update
   the pinned hash, and rebuild the image in the same change — one version, one place.

## Corrective Actions

- [ ] Resolve squawk in `gate_sql_lint.py` from the repository-vendored artifact, not the venv
- [ ] Remove the hand-placed `.venv/bin/squawk` (2.65.0) after the gate points at the repo copy
- [ ] Add squawk to `setup_venv.sh` so the gate binary is reproducible from the repository
- [ ] Add a version assertion (gate squawk == image squawk) and pin `sqlfluff` in requirements
- [ ] Register the vendored binary as a CI so the artifact the runtime trusts is governed

## Scope

- **In scope**: the commit-time SQL lint gate, the vendored squawk artifact, the migration
  sidecar image's lint stage, `setup_venv.sh`, and the verification that keeps them aligned.
- **Out of scope**: the migration pipeline's other stages (Flyway history repair, dynamic
  migration intents, dry-run), the DB image's plpgsql_check/pgTAP provisioning, and the
  `.squawk.toml` rule configuration.
