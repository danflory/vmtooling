# Guest JCode Deployment Rework Remove Host SSD Home Association

## Problem Statement

The sandbox must run jcode as a **standard, self-contained install**: its home is the
guest's own `~/.jcode` on the guest disk, and **nothing about it is associated with the
host**. Node **N10/RES-14** (`02_Research/14_JCode_Home_On_Host_SSD.md`, UDRS 50034)
designed the opposite — a dedicated jcode sandbox home on the host SSD, exposed into the
guest as a writable virtiofs share (domain target `vm_sandbox_jcode`, host backing
`/data/vm-sandbox/jcode-home` on `/dev/sdb1`, guest path `/mnt/vm-sandbox-jcode`) — so
that jcode state would outlive a disposable VM.

The design was **reverted** on 2026-09-16/17 (the document is WITHDRAWN, N10 is
SUPERSEDED, and the operator reports the idea "did not work out at all" after two days of
confusion). **The revert did not remove the wiring.** The environment was un-pointed
(`JCODE_HOME` commented out, guest fstab line commented, `*.bak.20260916-n10-revert`
artifacts) while the *topology* stayed in place:

- the `sandbox` domain still exports `vm_sandbox_jcode` **and** an unused `vm_sessions`;
- the guest still holds an **ad-hoc** read-write mount of `/mnt/vm-sandbox-jcode` (not in
  fstab, so it vanishes on reboot while the domain keeps exporting it) with stale 15–16
  Sep content;
- the host still holds the binds and backing directories, including a never-wired
  `jcode_state` directory.

Consequence: for a period the guest had **two plausible jcode homes** — the host-SSD share
and the guest-local `~/.jcode` — with neither authoritative and nothing in fstab to
disambiguate. The operator attributes two days of confusion to exactly this. The DAR's own
closure gate cannot see it (see the TP Change Report), so the residue can survive a
passing TP-188.

## Root Cause

The withdrawal was executed as an **environment change** (unset a variable, comment a line)
rather than as a **topology change** (detach the device, unmount, remove the binds and the
backing store). Documentation and running state were then allowed to disagree: the papers
said "abandoned" while the domain, the guest and the host filesystem still implemented it.
A withdrawn mechanism that remains reachable is worse than either keeping it or removing it,
because the record and the reality point in opposite directions and a reader has no way to
tell which is live.

The underlying process gap is the same one that let a vestigial native Postgres survive on
the guest (recorded in `02_Research/22_In-Guest_FIDO2_Signing_Enablement.md`, UDRS 50215):
**the verification artifacts assert the presence of the named object rather than the absence
of the mechanism**, so removal work is never actually tested. TP-188 Step 2 asks that "jcode
state present" in the guest and passes while a host-backed home is exported and mounted.

## Fix Description

1. **Domain**: detach the `vm_sandbox_jcode` filesystem device from the `sandbox` domain
   (persistent config, plus live where libvirt supports it).
2. **Guest**: unmount `/mnt/vm-sandbox-jcode`; confirm no jcode process or config references
   it.
3. **Host**: remove the `vm_sandbox_jcode` and `vm_sessions` bind entries and their
   `/etc/fstab` lines (operator sudo window).
4. **Host**: remove the now-unreferenced `/data/vm-sandbox/jcode-home`,
   `/data/jcode-vm-sessions` and `/var/lib/libvirt/virtiofs/jcode_state`.
5. **Verification**: add a TP-188 step that fails pre-fix and passes post-fix, asserting the
   guest's jcode home is guest-local and that no host-backed jcode share is exported or
   mounted.
6. **Record**: mark N10/N11 in the DAR graph as reworked/abandoned with a reference to this
   SPR, so the documentation matches the topology.

Untouched, deliberately: `host_dev_env` (read-only, RD-6), `vm_backups` (read-write), and
the **host's own** `~/.jcode` bind on the SSD, which is correct and working.

## Corrective Actions

- [ ] Detach the `vm_sandbox_jcode` filesystem device from the `sandbox` domain
- [ ] Unmount `/mnt/vm-sandbox-jcode` in the guest and verify nothing references it
- [ ] Remove the host binds and `/etc/fstab` lines for `vm_sandbox_jcode` and `vm_sessions`
- [ ] Remove the backing directories (`/data/vm-sandbox/jcode-home`, `/data/jcode-vm-sessions`, `/var/lib/libvirt/virtiofs/jcode_state`)
- [ ] Add the TP-188 step that asserts a guest-local jcode home and no host-backed share
- [ ] Mark N10/N11 in the DAR graph with the rework/abandonment and this SPR's id

## Scope

- **In scope**: the guest's jcode deployment topology (libvirt device, guest mount, host
  binds, backing directories) and the verification that keeps it that way; the graph
  marking for N10/N11.
- **Out of scope**: the host's own jcode home and storage (correct as-is); jcode binaries,
  config content or session data; the `sync.sh --jcode` snapshot path; anything about the
  FIDO2 sidecar (separate work in research 22).
