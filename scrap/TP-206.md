# TP-206 — Squawk lint gate and runtime sidecar parity

Verifies that the DB migration pipeline's **two squawk lint stages run one versioned binary
from one source**. Covers SPR-1137 (breaks B-1 rule divergence, B-2 not reproducible, B-3
ungoverned artifact). One step per VCL; all assertions are binary.

**Preconditions**: run from the repository root of a clone. Step 3 additionally needs the
`overwatch` namespace with `firecontrol-db-0` running (the migration sidecar container).
Step 6 needs database access (the `overwatch_agent` credential via `~/.pgpass`).

**How to run**: execute each step verbatim and record the raw output. A step passes only on the
stated evidence. This TP is expected to **FAIL** in the pre-fix state (that FAIL is the
regression evidence) and **PASS** after the SPR-1137 fix.

## Step 1 — the gate runs from a clean checkout (V-2 / B-2)

Create a compliant, unregistered migration fixture and stage it, then run the A6 gate with no
manual installs:

```bash
printf -- '-- fixture\nSELECT 1;\n' > firecontrol/sql/V999__tp206_fixture.sql
git add firecontrol/sql/V999__tp206_fixture.sql
.git/hooks/gates/A6_migration_lint.sh; echo "exit=$?"
git reset -q firecontrol/sql/V999__tp206_fixture.sql && rm -f firecontrol/sql/V999__tp206_fixture.sql
```

**Pass**: the gate exits 0 (or blocks only for the unregistered fixture, not for a missing
binary) **and** the output names the squawk binary it used, resolved from the repository.
**Pre-fix**: FAIL — in a venv without `squawk` the gate raises `FileNotFoundError` and exits
non-zero; measured today in `Overwatch_1` (no venv), `Overwatch_3` and `Overwatch_5`.

## Step 2 — the gate resolves the repository-vendored artifact (V-1 / B-1)

```bash
grep -rn 'sys.executable' firecontrol/gates/gate_sql_lint.py
grep -rn 'squawk' firecontrol/gates/gate_sql_lint.py | head -5
```

**Pass**: the gate resolves squawk from the repository path
(`firecontrol/docker/squawk-linux-x86_64`, or a path the repository installs) and no
`Path(sys.executable).parent`-relative resolution remains.
**Pre-fix**: FAIL — `_SQUAWK = str(_VENV_BIN / "squawk")` with
`_VENV_BIN = Path(sys.executable).parent`.

## Step 3 — gate version equals image version (V-3 / B-1)

```bash
echo -n "gate:  "; firecontrol/docker/squawk-linux-x86_64 --version
echo -n "image: "; sudo k3s kubectl exec -n overwatch firecontrol-db-0 -c migration-sidecar -- squawk --version
```

**Pass**: identical version strings.
**Pre-fix**: FAIL — the gate's venv binary is 2.65.0 while the image's vendored binary is
2.59.0 (the step compares the *gate's resolved* binary; with F-2 applied both are the vendored
2.59.0 and the assertion holds mechanically).

## Step 4 — no hand-placed gate binary; both engines provisioned (V-1, V-2 / B-2)

```bash
test -x .venv/bin/squawk && echo "HAND-PLACED BINARY PRESENT" || echo "no hand-placed squawk"
grep -n 'squawk' setup_venv.sh || echo "setup_venv.sh does NOT provision squawk"
grep -rn -i 'squawk\|sqlfluff' requirements*.txt || echo "neither engine pinned in requirements"
```

**Pass**: no hand-placed binary, and `setup_venv.sh` plus `requirements*.txt` account for both
gate engines (squawk and sqlfluff).
**Pre-fix**: FAIL — `.venv/bin/squawk` exists (2.65.0), `setup_venv.sh` provisions only
`sqlfluff`, and neither is pinned.

## Step 5 — one non-compliant migration, same verdict at both stages (V-4 / B-1)

```bash
printf -- '-- fixture: non-compliant\nALTER TABLE auth.udrs ADD COLUMN tp206_probe int NOT NULL;\n' > /tmp/tp206_bad.sql
firecontrol/docker/squawk-linux-x86_64 /tmp/tp206_bad.sql; echo "gate-side exit=$?"
sudo k3s kubectl exec -i -n overwatch firecontrol-db-0 -c migration-sidecar -- squawk - < /tmp/tp206_bad.sql; echo "runtime-side exit=$?"
rm -f /tmp/tp206_bad.sql
```

**Pass**: both stages return the same verdict (both flag, or both accept) for the same file.
**Pre-fix**: FAIL whenever a rule differs between the two versions; note that on the current
corpus the versions happen to agree (measured: identical 42 of 251 files), so this step is the
guard against future drift rather than a present-tense failure.

## Step 6 — the vendored binary is a governed CI (V-5 / B-3)

```bash
sha256sum firecontrol/docker/squawk-linux-x86_64
python3 OW_tools/db_write.py query_ci_by_path --path firecontrol/docker/squawk-linux-x86_64
```

**Pass**: the SHA-256 matches the pinned value recorded by RFC-OW-271 (`547623c6…24cafb`) and
the path resolves to a UDRS row.
**Pre-fix**: FAIL — the path is not registered (no UDRS row), while its companion
`firecontrol/.squawk.toml` is (UDRS 42031).
